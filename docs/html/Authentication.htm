Authentication

SmtpClient, Pop3Client and ImapClient all authenticate using SASL (Simple Authentication and Security Layer) mechanisms. This topic explains how MailKit chooses a mechanism and how to choose one yourself.

Authenticating with a user name and password

After connecting, the AuthenticationMechanisms property contains the list of SASL mechanisms advertised by the server. When you call Authenticate with a user name and password (or an ICredentials), MailKit picks the strongest mechanism that is supported by both the client and the server:

C# 
                    public static void AuthenticateWithCredentials ()
{
    using (var client = new ImapClient ()) {
        client.Connect ("imap.example.com", 993, SecureSocketOptions.SslOnConnect);

        // The AuthenticationMechanisms property contains the SASL mechanisms advertised by the server.
        Console.WriteLine ("Supported mechanisms: {0}", string.Join (", ", client.AuthenticationMechanisms));

        // MailKit will pick the strongest mechanism supported by both the client and the server.
        client.Authenticate (new NetworkCredential ("username", "password"));

        client.Disconnect (true);
    }
}

MailKit chooses from the mechanisms advertised by the server in the following order of preference:

Mechanism

Notes

SCRAM-SHA-512(-PLUS), SCRAM-SHA-256(-PLUS), SCRAM-SHA-1(-PLUS)

The password is never sent to the server. The -PLUS variants are preferred when the server advertises them because they bind the authentication to the TLS session (see Channel binding).

NTLM

See NTLM and Kerberos.

DIGEST-MD5, CRAM-MD5

Legacy challenge-response mechanisms based on MD5. Skipped on platforms where MD5 is unavailable (such as when FIPS mode is enforced).

PLAIN, LOGIN

The password is sent to the server (base64-encoded, not encrypted), so these should only be used over a TLS connection.

If none of these mechanisms are available, ImapClient falls back to the IMAP LOGIN command (unless the server advertises LOGINDISABLED) and Pop3Client falls back to the USER/PASS commands. Pop3Client also uses the APOP command, in preference to SASL, if the server supports it.

Mechanisms that require something other than a password, such as XOAUTH2, OAUTHBEARER, GSSAPI and ANONYMOUS, are never chosen automatically. To use them, see Choosing a mechanism.

If authentication fails, an AuthenticationException is thrown and the client remains connected so that you can try again.

Preventing MailKit from using a mechanism

Some servers advertise mechanisms that do not work correctly (or that are not enabled for a particular account), and a few servers will drop the connection or lock the account after a failed attempt. To prevent MailKit from trying a mechanism, remove it from AuthenticationMechanisms after connecting and before authenticating:

C# 
                    public static void RemoveAuthenticationMechanisms ()
{
    using (var client = new SmtpClient ()) {
        client.Connect ("smtp.example.com", 587, SecureSocketOptions.StartTls);

        // Prevent MailKit from trying mechanisms that we know are broken or undesirable
        // for this particular server. This must be done after Connect() and before
        // Authenticate().
        client.AuthenticationMechanisms.Remove ("NTLM");
        client.AuthenticationMechanisms.Remove ("CRAM-MD5");
        client.AuthenticationMechanisms.Remove ("DIGEST-MD5");

        client.Authenticate ("username", "password");

        client.Disconnect (true);
    }
}

Choosing a mechanism

To use a specific mechanism, create an instance of the corresponding SaslMechanism subclass and pass it to Authenticate:

C# 
                    public static void AuthenticateWithSaslMechanism ()
{
    using (var client = new ImapClient ()) {
        client.Connect ("imap.example.com", 993, SecureSocketOptions.SslOnConnect);

        var credentials = new NetworkCredential ("username", "password");
        SaslMechanism sasl;

        // Explicitly choose a mechanism rather than letting MailKit pick one.
        if (client.AuthenticationMechanisms.Contains ("SCRAM-SHA-256-PLUS"))
            sasl = new SaslMechanismScramSha256Plus (credentials);
        else if (client.AuthenticationMechanisms.Contains ("SCRAM-SHA-256"))
            sasl = new SaslMechanismScramSha256 (credentials);
        else
            throw new AuthenticationException ("The server does not support SCRAM-SHA-256.");

        client.Authenticate (sasl);

        // SCRAM-*-PLUS mechanisms bind the authentication to the underlying TLS channel.
        Console.WriteLine ("Channel binding negotiated: {0}", sasl.NegotiatedChannelBinding);

        client.Disconnect (true);
    }
}

Create and TryCreate can be used to create a mechanism by name, and IsSupported(String) checks whether MailKit supports a mechanism on the current platform.

Channel binding

Channel binding ties the authentication exchange to the underlying TLS session. Even if an attacker manages to intercept the TLS connection (for example, by using a fraudulent certificate), the server will reject the authentication because the TLS session the client sees is different from the one the server sees.

The SCRAM-*-PLUS mechanisms always use channel binding, and the NTLM and GSSAPI mechanisms can optionally use it. After authenticating, the NegotiatedChannelBinding property indicates whether channel binding was used.

OAuth 2.0, NTLM and Kerberos

Many providers (including Gmail and Microsoft 365) no longer allow password authentication and require OAuth 2.0 instead; see OAuth 2.0. For authenticating to Microsoft Exchange and other servers that use Windows authentication, see NTLM and Kerberos.
