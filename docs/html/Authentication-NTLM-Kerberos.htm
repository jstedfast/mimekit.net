NTLM and Kerberos

Microsoft Exchange (on-premises) and other servers in Windows domain environments often support Windows authentication using the NTLM and/or GSSAPI (Kerberos) SASL mechanisms. These allow an application to authenticate using domain credentials, or as the currently logged-in user without needing to know the user's password at all.

NTLM

MailKit includes two implementations of the NTLM mechanism:

Class

Description

SaslMechanismNtlm

A fully managed implementation that is available on all target frameworks and platforms. It requires an explicit user name and password.

SaslMechanismNtlmNative

Uses the operating system's implementation via NegotiateAuthentication. Only available on .NET 8 and later, and only on platforms where NTLM is supported (Windows, or Linux/macOS with the appropriate GSSAPI libraries installed). It can authenticate as the currently logged-in user.

When MailKit selects NTLM automatically (see Authentication), it uses SaslMechanismNtlmNative if it is supported on the current platform and falls back to SaslMechanismNtlm otherwise.

To use the managed implementation explicitly, pass the domain as part of the NetworkCredential. Setting the ServicePrincipalName and enabling AllowChannelBinding help protect against relay and man-in-the-middle attacks:

C# 
                    public static void AuthenticateWithNtlm ()
{
    using (var client = new SmtpClient ()) {
        client.Connect ("mail.corp.example.com", 587, SecureSocketOptions.StartTls);

        var ntlm = new SaslMechanismNtlm (new NetworkCredential ("username", "password", "DOMAIN")) {
            // The workstation name defaults to Environment.MachineName.
            Workstation = "MY-WORKSTATION",

            // Including the SPN in the NTLMv2 response helps protect against relay attacks.
            ServicePrincipalName = "SMTPSVC/mail.corp.example.com",

            // Channel binding ties the authentication to the TLS session, which protects against
            // man-in-the-middle attacks. It is currently opt-in for the managed NTLM implementation.
            AllowChannelBinding = true
        };

        client.Authenticate (ntlm);

        Console.WriteLine ("Channel binding negotiated: {0}", ntlm.NegotiatedChannelBinding);

        client.Disconnect (true);
    }
}

To authenticate as the currently logged-in user with the native implementation, use the default constructor, which uses DefaultNetworkCredentials:

C# 
                    public static void AuthenticateWithNtlmNative ()
{
    using (var client = new ImapClient ()) {
        client.Connect ("mail.corp.example.com", 993, SecureSocketOptions.SslOnConnect);

        // The default constructor uses CredentialCache.DefaultNetworkCredentials, which
        // means that the credentials of the currently logged-in user will be used.
        var ntlm = new SaslMechanismNtlmNative () {
            DesiredChannelBinding = ChannelBindingKind.Endpoint
        };

        client.Authenticate (ntlm);

        client.Disconnect (true);
    }
}

  Caution

NTLM is an old protocol with known weaknesses: it is vulnerable to relay attacks, and the cryptography it uses (HMAC-MD5 for NTLMv2) is weak by modern standards. Only use NTLM over a TLS connection, and prefer Kerberos (GSSAPI) or OAuth 2.0 (see OAuth 2.0) whenever the server supports them. Microsoft has deprecated NTLM in favor of Kerberos.

Kerberos (GSSAPI)

SaslMechanismGssapi implements the GSSAPI mechanism using Kerberos via NegotiateAuthentication. It is only available on .NET 8 and later; use IsSupported(String) to check whether the current platform supports it. On Linux and macOS, the system's GSSAPI libraries must be installed and the user must have a valid Kerberos ticket (for example, obtained using kinit).

Kerberos authenticates to a specific service, identified by a service principal name (SPN). If ServicePrincipalName is not set, MailKit uses SMTPSVC/<host>, which is only correct for SMTP. For IMAP and POP3, set it explicitly (usually imap/<host> or pop/<host>, but this depends on how the server is configured):

C# 
                    public static void AuthenticateWithGssapi ()
{
    using (var client = new ImapClient ()) {
        client.Connect ("mail.corp.example.com", 993, SecureSocketOptions.SslOnConnect);

        if (client.AuthenticationMechanisms.Contains ("GSSAPI") && SaslMechanism.IsSupported ("GSSAPI")) {
            // Use the Kerberos ticket of the currently logged-in user.
            var gssapi = new SaslMechanismGssapi () {
                // The SPN identifies the service that we are authenticating to. For IMAP, this
                // is normally "imap/<fqdn>". If not set, MailKit uses "SMTPSVC/<host>".
                ServicePrincipalName = "imap/mail.corp.example.com"
            };

            client.Authenticate (gssapi);
        } else {
            client.Authenticate ("username", "password");
        }

        client.Disconnect (true);
    }
}

  Note

The host name used in the SPN must be the server's fully qualified host name as known to the Kerberos realm. Connecting via an IP address or an alias (CNAME) commonly causes Kerberos authentication to fail.

Channel binding

For both SaslMechanismNtlmNative and SaslMechanismGssapi, set DesiredChannelBinding (for example, to ChannelBindingKind.Endpoint) to bind the authentication to the TLS session. After authenticating, NegotiatedChannelBinding indicates whether channel binding was used. Servers that enforce Extended Protection for Authentication (EPA) require channel binding.
